gander / FreeBSD の場合

FreeBSD でのプロセスビューア

新しいターミナルのプロセスビューアは、FreeBSD で減っていきます。データが難しいからではなく、そこでテストするプロジェクトが少ないからです。

htop は長年 FreeBSD に対応しており、gander には専用の sysctl/libkvm バックエンドがあり、CI の実 FreeBSD カーネルでテストされます。新しいツールのどれにするかを FreeBSD 上で選ぶなら、プラットフォーム対応の行がそのまま決め手になることが多いです。

実際に FreeBSD に対応しているのは誰か

FreeBSD 対応
htopはい。ports ツリーにあります
ganderはい。libkvm バックエンド、CI の VM でテスト
btopはい。CI でビルド(NetBSD、OpenBSD も)
bottom非公式と明記。「限定されたサポートのみの場合がある」

ツールの順位付けではありません。bottom は良いプログラムで、自分の FreeBSD サポートがどういうものかをはっきり述べています。言いたいことはもっと狭いです。FreeBSD では、他のどの行より先にこの行を確認すべきです。コンパイルはできるのにプラットフォーム上で動かされていないビューアは、遅かれ早かれ「欠けている」のではなく「間違った」数値を見せます。

gander が FreeBSD で読むもの

バックエンドは 2 つのインターフェースを使います。sysctl がプロセステーブルとシステムの数値を供給し、libkvm(kvm_getswapinfo、devstat_getdevs)が sysctl が公開していない部分を埋めます。

数値ソース
プロセス一覧sysctl(KERN_PROC_PROC) → kinfo_proc[]
CPU 時間、開始時刻ki_runtime(マイクロ秒)、ki_start
常駐サイズと仮想サイズki_rssize(ページ)、ki_size(バイト)
状態文字ki_stat と ki_tdflags/ki_slptime
コマンドライン、環境変数sysctl(KERN_PROC_ARGS)、KERN_PROC_ENV
実行ファイル、cwdKERN_PROC_PATHNAME、KERN_PROC_CWD
開いているファイルKERN_PROC_FILEDESC
コアごとの CPUkern.cp_times
メモリvm.stats.vm.v_* と v_page_count
スワップkvm_getswapinfo(3)
ディスクスループットdevstat_getdevs(3)
ネットワークスループットsysctl(NET_RT_IFLIST)
CPU アフィニティcpuset_getaffinity / cpuset_setaffinity

上の行のどれもが、開発中に「他のツールとの比較でしか見つからない」バグを 1 つは生みました。知っておく価値のあるものをいくつか:

  • ki_runtime はマイクロ秒です。Linux と macOS のすべての CPU 時間フィールドはチックカウンタです。これを HZ の除数で割ると、パーセンテージが 4 桁ずれます。
  • ki_rssize はページ、ki_size はバイトです。見た目は対に見えて、違います。ページサイズを忘れると、1.2 GB のプロセスが 300 MB と報告されます。レビューを生き抜けるくらいもっともらしい数字です。
  • ki_stat は状態文字ではありません。SSLEEP は ki_tdflags & TDF_SINTR と ki_slptime で 3 つに分かれます。算術的にマップすると、生まれたばかりのプロセスが I に、ロックされたものが X に表示されます。
  • kvm_getswapinfo はページ単位で報告します。htop 自身の FreeBSD バックエンドはページサイズではなく 1024 を掛けるので、1 GiB のスワップファイルが 4 MiB と、バイトと銘打たれて報告されます。gander は swapinfo(8) と同じやり方をします。
  • hw.physmem は VM が実際に管理するメモリより大きいので、これをメモリバーの分母にすると、バーは永遠に満タン手前で止まります。本当にメモリが尽きたマシンでは、描画バグに見えます。

FreeBSD にないものを、gander はそう言う

macOS と同じ規則です。- しか描けない列は列リストから外し、メーターは n/a here のまま残ります。設定ファイルをマシン間で移動させても読み込めるようにです。

FreeBSD 上
PSS / EPSSsmaps_rollup がない。対象外
PSI、zram、zswap、HugePagesメーターは n/a here と表示
コンテナ列jail はコンテナではない。対象外
GPU 列drm-usage-stats がない。対象外
遅延統計TASKSTATS は Linux 専用。対象外
I/O 優先度(i)ioprio_set がなく、パネルがその旨を表示
ファイルロックパネル(x)ロックテーブルがない。lsof への言及を表示
CPU アフィニティ、環境変数、開いているファイル対応
ホスト全体のディスクスループット対応。両方の数値を持つ唯一のプラットフォーム

jail は興味深い欠落です。kinfo_proc.ki_jid は読んでいて利用できますが、何も表示しません。jail はカーネルを共有し、イメージレイヤーを持たず、小さな整数以外の識別子もありません。これを CONTAINER と並べるのは誤った等価扱いです。jid 0 はホストで、それが普通の状態なので、その列は例外の少ないゼロの羅列になります。

テストの方法

FreeBSD には GitHub 提供のランナーがないため、2 つの方法で確認します。push ごとにクレート全体を x86_64-unknown-freebsd へクロスコンパイルするのと、QEMU 上の FreeBSD 14 VM の中でテスト一式を実行するのとです。重要なのは VM のジョブです。ライブテストは、ゲスト内で gander の数値を ps(1)、sysctl(8)、swapinfo(8)、netstat(1) と照合します。上に挙げたバグの大半は、クロスコンパイルでは見えないものです。

各プラットフォームで意図的に欠けている行すべてを含む完全なマトリクスは、docs/PORTABILITY.md にあります。

FreeBSD へのインストール

リリースごとに x86_64-unknown-freebsd アーカイブと、その隣に .sha256 ファイルを出します:

tar -xzf gander-<version>-x86_64-unknown-freebsd.tar.gz
./gander-<version>-x86_64-unknown-freebsd/gander

Rust ツールチェーンがあれば:

cargo install gander-bin

最新のアーカイブは Release を、すべてのインストール方法はインストール節を見てください。
