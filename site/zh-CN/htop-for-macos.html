gander / 在 macOS 上

macOS 上的进程查看器

htop 在 macOS 上是能用的。让人栽跟头的不是 htop——而是他们期待中的几个 Linux 数字在 macOS 上没有对应物,谁照样显示谁就是在猜。

这一页是一份清单:macOS 会告诉进程查看器什么、不肯告诉什么,以及 gander 对每处空缺怎么处理。它对 htop 和 gander 同样适用,因为两者读的是同一批接口。

安装 gander 后端说明

macOS 肯给你的

htop 进程表里的东西几乎都来自三个地方,这三处在 macOS 上都可用:

数字来源
进程列表proc_listallpids 加 PROC_PIDTASKALLINFO
命令行sysctl(KERN_PROCARGS2)
可执行文件路径proc_pidpath
工作目录proc_pidinfo(PROC_PIDVNODEPATHINFO)
线程PROC_PIDLISTTHREADS + PROC_PIDTHREADINFO
内存总量、swaphost_statistics64、hw.memsize、sysctl(vm.swapusage)
每核 CPUhost_processor_info
网络吞吐sysctl(NET_RT_IFLIST2)

所以「htop 在 macOS 上其实用不了」这个常见说法是错的。能用。有意思的是第二张表。

macOS 不肯给的

这里的每一行都是只有 Linux 才有的机制,没有 Darwin 对应物。

gander 在 macOS 上
每进程 PSS / EPSS没有这一列,而不是显示 -
PSI 压力 metermeter 显示 n/a here
Zram / Zswap / HugePagesmeter 显示 n/a here
容器 / cgroup 身份没有 cgroup 概念;这一列被排除
CPU 延迟统计列被排除
I/O 优先级(i)没有 ioprio_set;面板会说明
GPU 列需要 IOKit;被排除
主机级磁盘吞吐meter 显示 n/a here
CPU 亲和性编辑仅提示

要紧的区分是「没有这一列」和「这一列显示 -」。列里的 - 读作「这个进程此刻没有这个值」;没有这一列读作「这个系统没有这个概念」。在 macOS 上,gander 把这些列从设置界面整个排除,meter 则留在原处显示 n/a here——因为在 Linux 上写好的配置文件还得能在 Mac 上加载,消失的 meter 是坏配置,不是诚实的配置。

内存:那个被人当成 bug 的数字

macOS 的内存记账不是 Linux 那一套,硬把一套映射到另一套的查看器会错得很显眼。vm_statistics64 暴露了两个互相重叠的计数家族——按使用(active、inactive、wire、compressor、free、speculative)和按后端存储(internal、external)——跨家族相加就会重复计数。gander 用后端存储家族加上它没覆盖的两类页来构建这个数字:

used      = (internal - purgeable) + wired + compressed
available = total - used

这个数字和 htop 打印的一致,推导方式也一致,和「活动监视器」与 top 报告的也一致。所以在 Mac 上 gander 和 htop 互相吻合。两者都不吻合的,是从 vm_stat 天真地算 total - free——正是那种让谁看都像错了的对比。

把 inactive 和 speculative 算作缓存,不算已用。开机一周的机器不会因为 inactive 很大就内存告急——那是可以回收的。

在 Mac 上 gander 和 htop 的差别

数字一致,屏幕不一致。htop 的细节面板都是全屏模式:e 看环境变量、l 看打开的文件、s 看系统调用,每个都会顶掉进程表,回来还得重新找位置。gander 把选中进程的命令行、状态、内存和运行时间放在表格旁边的一列里,列表原地不动。

按键相同,htoprc 导入相同;按 L 就能得到 htop 的布局,如果你要的就是那个。有差别的按键见 vs htop。

在 macOS 上安装

brew install pandasir/tap/gander

# 或者,有 Rust 工具链的话
cargo install gander-bin

Release 里也有 Apple Silicon 和 Intel 两个架构的预编译压缩包。

macOS 上的实时测试会读真实的进程表,测试套件可能需要在非受限沙箱之外运行。三个平台的后端对比见 docs/PORTABILITY.md。
