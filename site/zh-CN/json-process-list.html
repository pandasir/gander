gander / 给脚本用的 JSON 进程列表

给脚本用的 JSON 进程列表

TUI 显示的数字,每次采样一份 JSON 文档——给 cron 任务、监控,以及一切本来要去解析等宽 ps 输出的东西。

要一次性的列输出,用 ps;那仍是它的主场。要在 Linux、macOS 和 FreeBSD 上把内存百分比、完整命令行和字节精确的大小当数据用,用 gander --json。要实时 CPU 百分比,同一次调用里至少采两个样;第一个样本没有 CPU 基线。

别的工具能给脚本什么

ps 输出一份用空格对齐的列的快照,所以每台服务器上总有一半脚本藏着一句 awk,列一改名就断。它的 CPU 数字是进程一生的平均值,不是现在在干什么;想同时拿到不截断的 comm 和完整命令行,procps 和 Darwin 的参数还各不相同。

top 有批处理模式(-b),但它批处理的是渲染出来的 curses 屏幕——是显示屏的文字刮取,不是数据。htop 完全没有批处理模式:没法向它要任何东西的一个采样。btop 处境相同,bottom 也是。

这个空缺就是 shell 脚本最后都自己手读 /proc、每个平台读一遍的原因。gander 的 TUI 和批处理模式读的是同一批后端——Linux 用 /proc,macOS 用 sysctl/Mach/libproc,FreeBSD 用 sysctl/libkvm——脚本看到的数字就是交互视图显示的数字。

批处理模式

gander --json                       # 一次 JSON 采样,然后退出
gander --json --limit 5             # 最多五行
gander --json --sort PERCENT_MEM    # 和 TUI 的 F6 同样排序
gander --json -F "postgres|nginx"    # 固定字符串过滤,不是正则
gander -n 60 -d 1000 --json         # 六十次采样,间隔约一秒

一次调用打印一个 JSON 进程行数组然后退出。用 -n N 会连着打印 N 个数组——一串文档,所以 jq -s 'add' 能把整次运行摊平成一个列表。排序和过滤发生在生成 JSON 之前,所以 --limit 5 打印五行就停——不会先建出整张表再裁掉。

cpu_percent 需要同一进程的两次连续采样。每次调用都从全新的采样器开始,所以第一个样本里每行的 CPU 都是零;后到的进程在后续采样里也从零开始。内存数字不需要这条基线。要给脚本或 cron 拿一个 CPU 采样,隔一秒采两个样,只留第二个数组:

gander -n 2 -d 1000 --json | jq -s '.[1]'

用 jq,内存最高的五个进程,制表符分隔:

gander --json --sort PERCENT_MEM --limit 5 |
  jq -r '.[] | [.pid, .mem_percent, .rss, .cmdline] | @tsv'

同一批行,合并一次一分钟的运行,抓那些突然冒头又消失的:

gander -n 60 -d 1000 --json | jq -s 'add |
  group_by(.comm) | map({comm: .[0].comm, max_rss: (map(.rss) | max)}) |
  sort_by(-.max_rss) | .[0:10]'

字段

一行真实数据,来自 macOS:

{"pid":407,"ppid":1,"uid":0,"comm":"loginwindow","state":"S",
  "cpu_percent":0.00,"mem_percent":0.18,"rss":15613952,
  "vsize":446144643072,"nice":0,"priority":0,"threads":6,
  "elapsed":479475,"is_thread":false,"identity":407,
  "cmdline":"/System/Library/CoreServices/loginwindow.app/Contents/MacOS/loginwindow console",
  "memory":null}
字段含义
pid、ppid、uid各 id,按内核报告的。
comm可执行文件的基名,TUI 默认排序的那一列。
cmdline完整命令行含参数,永不截断。这是 ps 让你费劲才能拿到的字段。
state内核的状态字母:R 运行、S 睡眠、Z 僵尸,等等。
cpu_percent相邻两次采样之间的 CPU 用量,不是一生平均值。没有上一次采样之前是零,包括每次调用的第一个样本里的每一行。
mem_percent采样当时的常驻内存占总物理内存的百分比;第一个样本就有。
rss、vsize常驻与虚拟大小,单位字节。不是「KB,大概吧」——正是那种让解析 ps 输出不可信的单位含糊。
nice、priority、threads调度数字,按内核报告的。
elapsed进程启动至今的秒数。
is_thread行是别的进程的线程而非进程本身时为 true;用 --threads 时逐线程的行也会输出。
identity数字行标识:进程行是 PID,线程行是线程专属 id。它用来区分 macOS 上共享 PID 的线程;不是容器标识,且始终存在。
memory随平台嵌套的内存与资源细节。macOS 和 FreeBSD 上为 null;Linux 上,未请求或拿不到的可选读取,各自的值为 null。

排序接受 TUI 的列名——PERCENT_CPU、PERCENT_MEM、M_RESIDENT、PID 等。它们不是 JSON 键名:想按 rss 排,用 --sort M_RESIDENT。-F 对命令行匹配大小写不敏感的固定字符串,用 | 分隔;它刻意不是正则——因为一个要按计划跑的过滤器,不该离「匹配一切」只差一个字符。

它不是什么

它不是监控 agent。每次调用自成一体:没有守护进程、没有存储、没有仪表盘、没有依赖。cron 任务可以把 gander --json 追加到文件里做内存快照;CPU 测量则改用上面的两次采样命令。文件仍然能被 jq 读。要带保留和告警的持续采集,把你已经在跑的工具指向这份输出,别指望 gander 长出服务器。

它也不是 ps。一次性的列输出、进程组选择和会话 id 是 ps 的强项,已经在用 ps 的脚本没有理由改。批处理模式留给 ps 不够用的场合:实时百分比、字节精确的大小,以及和交互视图一致的数字。

安装

brew install pandasir/tap/gander     # macOS
cargo install gander-bin             # 任何有 Rust 的平台

Debian、Ubuntu、Fedora 和 RHEL 的 Linux 包在签名软件源上;每个 Release 附带 macOS(Apple Silicon 和 Intel)、Linux(x86_64 和 arm64)和 FreeBSD 的压缩包。见所有安装方式。
